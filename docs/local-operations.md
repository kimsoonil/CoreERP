# 로컬 백업·복원·장애 복구·부하 검증

**개인 프로젝트 · 운영 배포 전.** 회사·게임·운영 DB를 연결하지 않고 새 임시 PostgreSQL의 합성 데이터만 사용했습니다. 실제 요청과 실제 DB로 수행한 로컬 실험이며, 외부 서비스의 처리량이나 복구 목표를 보장하지 않습니다.

## 무엇을 검사했나

### 논리 백업과 새 DB 복원

업무 요청이 멈춘 상태에서 `pg_dump -Fc --no-owner --no-acl`로 백업하고, 새 `coreerp_restore_test` DB에 `pg_restore --exit-on-error`로 복원했습니다. 기존 DB를 덮어쓰지 않습니다.

- 애플리케이션 스키마의 **25개 테이블**에 대해 행 수와 전체 행의 정렬된 JSON 지문이 일치하는지 비교했습니다. 사용자·권한·거래·재고·감사·일별 집계·Flyway 이력도 포함합니다. 지문 비교는 전송/복원 정합성 확인용이며 암호학적 보안 증명이 아닙니다.
- 모든 시퀀스의 `last_value`와 `is_called`를 비교했습니다.
- 음수 재고·음수 예약·현재고보다 큰 예약 행이 0개인지 검사했습니다.
- 복원 DB에 별도 Spring Boot를 8081 포트로 실행했습니다. Flyway 기동, 로그인, 상품 총건수와 기간 매출의 원본 API 대비 일치를 확인했습니다.
- 백업 파일은 임시 폴더에만 만들고 검사 종료 후 삭제합니다. 실제 DB 덤프나 비밀번호는 GitHub에 올리지 않습니다.

### 거래 중 DB 연결 단절과 재시도

테스트 전용 트리거가 출고 품목 저장 시 잠시 기다리게 한 뒤, 해당 DB 연결을 `pg_terminate_backend`로 종료했습니다. 재고 변경과 출고 헤더 저장이 시작된 트랜잭션에 실제 연결 장애를 발생시키는 방식입니다.

1. 첫 출고 API는 500으로 실패했습니다.
2. 현재고 10·예약 3, 주문 RESERVED, 출고 문서 0개로 전체 롤백을 확인했습니다.
3. 임시 트리거를 제거한 뒤 **동일 요청 키**로 재시도했습니다.
4. API가 DB 풀의 정상 연결로 처리해 200을 반환했고 현재고 7·예약 0이 됐습니다. 다시 같은 키로 요청해도 동일 출고 ID를 반환했습니다.

전체 PostgreSQL 프로세스 중단, 저장장치 손상, 네트워크 분리·failover·다중 인스턴스 복구는 이번 실험에 포함하지 않습니다. 오류가 났다고 출고를 새 키로 무조건 다시 만드는 대신 상태와 요청 키를 확인해야 합니다.

### HTTP 부하와 재고 경합

- 조회: 20회 워밍업을 제외하고, 상품·재고 서버 페이지 API를 동시 12개 작업으로 **최소 30초** 반복했습니다.
- 같은 상품 주문: 재고 25개에 100건을 동시 16개 작업으로 요청했습니다. 정확히 25건 예약 성공·75건 재고 부족 409, 예약 25·현재고 25를 검사했습니다.
- 중복 출고: 동일 주문에 서로 다른 요청 키로 출고 40건을 동시 12개 작업으로 요청했습니다. 모두 동일 출고 ID, 현재고와 예약 각각 1회 차감을 검사했습니다.

단일 관리자 세션, loopback HTTP, 같은 컴퓨터의 클라이언트·API·DB, Hikari 최대 연결 12개, 기본 demo 상품 1만 개·재고 3만 행에서 측정했습니다. 25개 단위 페이지를 순회하며 응답 전체를 읽을 때까지 시간을 잽니다. 동시 작업이 응답을 받은 뒤 다음 요청을 보내는 closed-loop 방식입니다. 실제 사용자 수·독립 세션 수를 뜻하지 않습니다.

## 실제 측정값

아래 표는 첨부 JSON의 관측값으로 작성합니다. 재측정하면 환경과 JIT·캐시·다른 프로세스의 영향으로 달라집니다. 단일 실행이며 통계적 신뢰구간은 제시하지 않습니다. 특히 주문·중복 출고 표본은 짧은 경합 시나리오이므로 지속 쓰기 처리량으로 해석하지 않습니다.

측정일: 2026-11-28(KST). Apple M4 / macOS arm64 / Node v24.19.0 / PostgreSQL 18.7, 백업 도구 pg_dump (PostgreSQL) 19.0.

| 시나리오 | 요청 / 동시 작업 | 실제 결과 | p50 / p95 |
| --- | --- | --- | --- |
| 조회 30.008초 | 50,317 / 12 | 200: 50,317건, 예상 밖 실패 0 | 6.93 / 12.06 ms |
| 재고 25개 주문 | 100 / 16 | 성공 25, 예상 재고 부족 409: 75 | 6.33 / 55.45 ms |
| 동일 주문 출고 | 40 / 12 | 200: 40건, 출고 문서 1개·단일 차감 | 5.96 / 16.34 ms |

조회 구간 처리율은 약 1,676.81요청/초였습니다. 같은 호스트·단일 세션의 짧은 실행 관측값이며 운영 처리량으로 제시하지 않습니다. 백업 82.42ms·복원 143.18ms는 도구 실행 시간만 재며, API 기동·검증·장애 탐지 시간을 포함한 RTO가 아닙니다.

## 재현 방법

Java 21·빌드된 API JAR, Node, PostgreSQL 서버, 서버 버전 이상인 `pg_dump`/`pg_restore` 클라이언트가 필요합니다. 기존 README로 **새 일회용 coreerp_demo DB**에 demo API를 8080으로 실행합니다. 새 빈 복원 DB는 도구가 생성하며, 이미 존재하면 덮어쓰지 않고 중단합니다. 8081 포트도 비어 있어야 합니다.

```sh
cd tools
npm ci
# DB_HOST=127.0.0.1, DB_PORT, DB_NAME=coreerp_demo, DB_USER, DB_PASSWORD
# APP_ADMIN_PASSWORD, APP_DEMO_PASSWORD: 방금 만든 로컬 demo API와 같은 값
# PG_BIN: pg_dump/pg_restore가 있는 디렉터리 (PATH에 있으면 생략)
# JAVA_BIN: Java 21 실행 파일 (PATH가 Java 21이면 생략)
# 필요하면 API_URL, API_JAR, EVIDENCE_OUTPUT 지정
export COREERP_LOCAL_OPERATIONS=1
npm run check:operations
```

비밀번호를 명령행 인자에 넣거나 결과 JSON·Git에 기록하지 마세요. 환경변수로만 전달합니다. 도구는 DB와 API 호스트를 localhost/127.0.0.1로 제한합니다. 생성한 상품·주문·감사 이력과 복원 DB는 실험 DB에 남으므로 **같은 DB에서 반복 실행하지 말고 새 임시 클러스터**를 준비하세요. 종료 후 임시 클러스터를 제거하면 됩니다. 실패 시에도 오류 유발 트리거·복원 API·임시 덤프는 정리합니다.

실행 코드는 [operations-check.mjs](../tools/operations-check.mjs)에 있습니다. 운영 검증은 의도적으로 DB 연결을 종료하므로 일반 CI 기본 작업에 자동 연결하지 않았습니다. [기존 업무·화면 CI](testing.md)와 구분합니다.
