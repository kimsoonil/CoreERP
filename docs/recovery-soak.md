# WAL 시점 복구·서비스 프로세스 장애·15분 지속 부하

**개인 프로젝트 · 운영 배포 전.** 기존 게임·ERP·회사 DB를 연결하지 않고 도구가 직접 생성한 두 임시 PostgreSQL 클러스터와 자식 API 프로세스만 사용했습니다. 실제 SQL·HTTP·물리 백업과 WAL을 사용합니다.

## WAL 시점 복구(PITR)

1. 새 PostgreSQL을 `wal_level=replica`, `archive_mode=on`으로 기동하고 demo 데이터와 상품 재고 20개를 생성합니다.
2. `pg_basebackup -Fp -X stream -c fast`로 물리 기본 백업을 만듭니다.
3. API에서 3개를 주문·출고하는 거래 A를 커밋합니다. 재고는 17개입니다. 모든 애플리케이션 테이블의 행 수·정렬된 전체 행 JSON 지문과 매출 API 결과를 저장합니다.
4. `pg_create_restore_point('coreerp_before_later_trade')`로 WAL 복구 목표를 기록합니다. 목표 LSN과 DB 시각도 결과에 남깁니다.
5. 거래 B로 4개를 추가 주문·출고합니다. 원본 재고는 13개입니다. WAL을 전환하고 해당 세그먼트가 아카이브에 저장될 때까지 확인합니다.
6. 기본 백업을 **새 디렉터리**에 복사하고 `recovery.signal`, `restore_command`, `recovery_target_name`, `recovery_target_action=promote`로 다른 포트에서 기동합니다.
7. 복구가 끝나 승격된 상태(`pg_is_in_recovery() = false`)까지 기다립니다. 복구된 25개 테이블 지문을 A 직후와 비교하고, B 주문 부재·재고 17개·복원 API 로그인과 매출 일치를 검사합니다.

이 검사는 WAL의 **이름 있는 복구 지점**을 대상으로 합니다. 임의 시간 문자열을 입력한 모든 복구나 원격 아카이브의 내구성을 검증한 것은 아닙니다. 물리 복구 시 시퀀스 값은 미리 기록된 범위만큼 건너뛸 수 있으므로 논리 백업 검사와 달리 정확히 같은 시퀀스 값을 요구하지 않습니다.

## API·PostgreSQL 전체 프로세스 장애 복구

별도 상품 재고 10개를 만들고 주문 3개를 예약합니다. 출고 품목 저장에서 임시 트리거가 기다리는 동안 `pg_ctl stop -m immediate`로 **PostgreSQL 인스턴스 전체**를 비정상 종료합니다. 현재 진행 중인 HTTP 출고가 500으로 실패하는지 확인한 뒤, 도구가 생성한 Java API도 SIGKILL로 종료합니다.

두 서비스를 다시 기동해 아래를 확인합니다.

- PostgreSQL 로그에서 비정상 중단 후 복구 흔적 확인
- 이전 커밋 거래 B와 재고 13개 보존
- 장애 중 출고 헤더·품목·재고 변경 롤백: 주문 RESERVED, 출고 0개, 현재고 10·예약 3
- API 프로세스 재시작으로 이전 메모리 세션은 401 처리, 재로그인 성공
- 같은 요청 키로 출고 재시도 200, 현재고 7·예약 0

**동일 호스트의 서비스 프로세스 장애** 실험입니다. 물리 서버 전원 차단, OS 커널 장애·디스크 손상, 네트워크 격리, 다른 노드로의 failover는 포함하지 않습니다. 자동 스크립트가 재기동하므로 사람의 장애 인지·판단·대응 시간도 측정하지 않습니다.

## 15분 혼합 지속 부하

- 실제 DB에 연결된 API, 독립 관리자 로그인 세션 **8개**
- 조회 작업 6개: 상품·창고 재고 서버 페이지(25개)·당일 매출을 번갈아 조회, 응답 후 40ms 대기
- 쓰기 작업 2개: 새 주문 예약 → 출고 → 출고 취소를 반복, 한 사이클 후 200ms 대기
- 30회 워밍업 제외, 최소 15분 동안 작업 유지. 마지막 요청의 완료까지 기다림
- 요청마다 상대 시각·업무 구분·HTTP 상태·전체 응답 수신 지연을 gzip CSV에 저장
- 분당 요청 수·p50·p95·p99·최대 지연·상태 분포, 약 1분 간격 API RSS와 DB 크기 기록
- 종료 후 예상 밖 HTTP 실패 0개, 실험 상품 현재고 100,000·예약 0, 전체 재고 불변식 위반 0개 검사

요청이 끝난 후 다음 요청을 보내는 paced closed-loop 방식입니다. 동시 작업 8개가 실제 활성 사용자 8명 또는 최대 처리량을 뜻하지 않습니다. 클라이언트·API·DB·WAL 아카이브가 같은 호스트와 저장장치를 사용합니다. 다른 데스크톱 프로세스·CPU 온도·냉 캐시를 통제한 실험은 아닙니다. 이전 30초 조회 전용 실험과는 요청 종류·대기 시간·독립 세션 수가 다르므로 처리율을 직접 비교하지 않습니다. API RSS 표본은 JVM 힙 사용량이 아니며, RSS가 안정적이라고 메모리 누수가 없다고 단정하지 않습니다.

## 재현

macOS/Linux의 POSIX 셸 환경, Java 21과 빌드된 API JAR, Node와 `tools/npm ci`, PostgreSQL 서버 바이너리(`initdb`, `postgres`, `pg_ctl`) 및 서버와 호환되는 `pg_basebackup` 클라이언트가 필요합니다. 일반 사용자로 실행합니다. Docker는 필수가 아닙니다.

```sh
cd tools
npm ci
# PG_SERVER_BIN: PostgreSQL 서버 바이너리 디렉터리
# PG_CLIENT_BIN: pg_basebackup 디렉터리 (서버와 같으면 생략)
# JAVA_BIN: Java 21 실행 파일 (PATH가 Java 21이면 생략)
# API_JAR: 기본 ../backend/target/coreerp-api-1.0.0.jar
export COREERP_RECOVERY_SOAK=1
export SOAK_MINUTES=15
npm run check:recovery-soak
```

`SOAK_MINUTES`는 15~120 사이 정수입니다. 임시 DB·자격증명을 도구가 새로 생성하므로 기존 DB 연결정보는 받지 않습니다. loopback 전용 DB 55448/55449와 API 8180/8181이 비어 있어야 하며, 사용 중이면 중단합니다. 기존 디렉터리·DB를 지정하거나 덮어쓸 수 없습니다. 종료 시 소유한 프로세스·기본 백업·WAL·임시 DB·비밀번호 파일을 정리하고, 공개 가능한 측정 JSON·CSV만 남깁니다.

기본 CI와 분리한 명시적 로컬 장애 실험입니다. 재현에는 15분 이상이 필요합니다. 오류가 발생한 실행을 성공 증거로 남기지 말고 원인을 고친 뒤 새 임시 환경에서 재실행해야 합니다.

## 남은 범위

임의 시각 기반 복구 매트릭스, 원격·암호화 백업 보관과 복구 훈련, 물리 서버 장애·스토리지 손상·다중 노드 failover, 24시간 이상 부하·포화점·다양한 사용자 역할·인터넷/TLS 지연은 미검증입니다. 이 실험 결과를 운영 RTO/RPO·무중단 보장으로 사용하지 않습니다. 운영 배포 전 상태를 유지합니다.
