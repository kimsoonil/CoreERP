# 운영 준비와 장애 대응

**운영 배포 전.** 아래 절차는 로컬 데모 운영 지침과 운영 전 확인 항목입니다. 외부 서버의 SLA나 보안 감사 완료를 주장하지 않습니다. [로컬 백업·복원·연결 장애·부하 검증](local-operations.md)을 완료했으며, 외부 운영 환경과 시점 복구는 별도 검증이 필요합니다.

## 데모 실행과 중단

README의 새 `.env`와 합성 DB로 `docker compose up --build -d --wait`합니다. `http://localhost:8088/api/health`가 응답하고 로그인·업무 조회가 되는지 확인합니다. `docker compose logs --tail=100 api db`로 기동·Flyway 실패를 확인할 수 있습니다. 로그를 공유하기 전에 개인정보·연결정보 포함 여부를 검토하세요.

`docker compose down`은 DB 볼륨을 보존합니다. `down -v`는 데이터를 삭제하므로 일반 종료에 사용하지 않습니다. demo 프로필을 default로 바꾸는 것만으로 합성 데이터가 제거되지는 않습니다.

## 업무 오류를 만났을 때

| 증상 | 먼저 확인 | 재시도 기준 |
| --- | --- | --- |
| 재고 부족 409 | 현재고·예약·가용, 대상 창고 | 수량/재고를 바로잡은 후 새 업무 입력 |
| 응답 유실·중복 클릭 | 문서 상태·요청 키 | 같은 내용은 같은 키로 재시도; UI 새로고침 후 키 복구는 미지원 |
| 부분 반영 의심 | 문서·재고·이력·감사 로그를 함께 조회 | DB를 직접 수정하지 말고 실패 원인 조사 |
| 배치 FAILED | 실행 날짜·오류 코드, 이전 성공 집계 | 원인 해결 후 같은 날짜 재실행 |
| BATCH_HISTORY_PENDING | 집계의 run ID·실행 이력 | 같은 날짜 재실행으로 커밋된 결과의 이력 복구 |
| 오래된 집계(stale) | 원본 버전과 집계 버전 | 닫힌 날짜 재집계; 당일은 실시간 보고서 사용 |

고장 유발 테스트는 별도 `_test` DB에서만 수행합니다. 운영 데이터에 오류 트리거를 넣어 실험하지 않습니다.

## 백업·복원 — 로컬 합성 DB 실습 완료

PostgreSQL의 `pg_dump -Fc`로 백업하고 **다른 빈 DB**에 `pg_restore --exit-on-error --no-owner`로 복원하는 방식입니다. 복원 후 Flyway 이력·기준정보·문서 수·재고 불변식·원본/집계 합계를 비교하고, 별도 앱 연결로 로그인과 조회를 검증해야 합니다. 실행 중인 DB 위에 복원하거나 기존 볼륨을 덮어쓰지 않습니다.

일회용 로컬 DB의 백업을 새 DB에 복원해 25개 테이블·시퀀스와 API 결과 일치를 확인했습니다. [실행 조건과 원본 결과](local-operations.md)를 참고하세요. 이 실험은 CI 기본 작업과 분리돼 있으며 시점 복구는 검증하지 않습니다. 백업 암호화·외부 보관·주기·보존 기간·복원 시간 목표는 실제 운영 환경을 정한 뒤 마련할 항목입니다.

## 외부 운영 전 남은 항목

- TLS와 Secure 쿠키, 외부 비밀 관리, 앱 DB 최소 권한 계정 분리
- 로그인 요청 제한·비밀번호 변경/재설정·세션 만료 정책
- 외부 환경의 백업 복원·시점 복구, 장애 알림·로그 보존·잠금 대기 관측
- 다중 서버 부하·DB 재시작·네트워크 장애 검증과 시간 제한 정책
- 요청 키와 배치 실행 이력의 보관·정리 정책
